# 피드백 채점 방식 변경 — API 계약 명세 (axis-v1)

- 대상: Repit API 서버 (`/feedback/solo`, `/feedback/multi` 콜백 수신측)
- 채점 방식 버전: `axis-v1`
- 작성일: 2026-09-28

이 문서는 두 부분으로 나뉜다.

1. **이번에 적용된 변경** — 와이어 형식(필드 이름·타입·구조)은 그대로이고, 점수 필드의 **산출 방식과 의미**가 바뀌었다.
   API 서버가 코드를 고치지 않아도 연동은 깨지지 않는다.
2. **다음 단계 계약 변경안(미적용)** — 사용자에게 "어느 축이 몇 점이라 최종 몇 점인지"를 보여주기 위한 필드 추가안이다.
   합의 후 반영한다.

---

## 1. 이번에 적용된 변경

### 1.1 요약

| 항목 | 변경 여부 |
|---|---|
| 요청 본문 형식 | 변경 없음 |
| 성공 콜백 형식(필드 이름·타입·필수 여부) | 변경 없음 |
| 성공 콜백 점수 필드의 **값 산출 방식** | **변경** — LLM 이 직접 매기던 값에서 서버 계산값으로 |
| 실패 콜백 형식·상태 코드 | 변경 없음 (실패 조건 1건 추가, 1.4 참고) |
| N:1 요청의 `personas[].role` | 형식 변경 없음. 값 `TECH` 가 채점에 쓰이기 시작함(1.5 참고) |

### 1.2 채점 구조

이전에는 LLM 이 `totalScore`, `intentAlignmentScore`, `reliabilityScore`, `personas[].score` 를 각각 0~100 으로 직접 매겼다.
세 값은 서로 독립적이라 "왜 이 점수인지"를 설명할 수 없었다.

이제 LLM 은 **답변한 문항마다 4개 축의 등급(0~4)** 과 **세션 전체의 일관성 등급(0~4)** 만 매기고,
점수는 서버가 아래 공식으로 계산한다.

| 축 | 보는 것 | 가중치 |
|---|---|---|
| 의도 충족 (intent) | 질문이 물은 것에 답했는가 | 35% |
| 깊이 (depth) | 이유, 대안 비교(트레이드오프), 한계 인식 | 25% |
| 구체성 (specificity) | 실제로 한 일과 방식, 결과 | 25% |
| 정확성 (accuracy) | 확립된 기술 개념과 맞는가. 기술 내용이 없는 질문은 해당 없음 | 15% |
| 일관성 (consistency) | 답변끼리 어긋나는 진술이 있는가 (세션 단위) | 종합 점수에 미반영 |

등급별 판정 기준은 `src/app/core/common/feedback/rubric.py` 에 있다.

**계산 규칙**

1. 등급 → 점수: 0/1/2/3/4 → 0/25/50/75/100
2. 축 점수 = 답변한 문항들의 해당 축 평균을 정수로 반올림(0.5 는 올림)
3. `totalScore` = 2 의 정수 축 점수로 가중합한 뒤 정수로 반올림
4. 의도 충족이 0등급(동문서답·회피)인 문항은 나머지 축도 0으로 처리
5. 정확성이 "해당 없음"인 문항은 정확성 평균에서만 빠진다.
   세션 전체가 해당 없으면 정확성을 빼고 나머지 세 축을 35:25:25 비율로 다시 나눈다.
6. 미답변 문항은 계산에서 빠진다(기존과 동일). `answeredCount` / `questionCount` 로만 드러난다.

**계산 예시** — 답변 2개, 등급 (의도, 깊이, 구체성, 정확성) = (4, 2, 3, 4), (3, 1, 2, 4)

| 축 | 계산 | 점수 |
|---|---|---|
| 의도 충족 | (100 + 75) / 2 = 87.5 | 88 |
| 깊이 | (50 + 25) / 2 = 37.5 | 38 |
| 구체성 | (75 + 50) / 2 = 62.5 | 63 |
| 정확성 | (100 + 100) / 2 | 100 |
| **totalScore** | (88×35 + 38×25 + 63×25 + 100×15) / 100 = 71.05 | **71** |

### 1.3 필드별 의미 변경

**`POST /feedback/solo` 성공 콜백 — `result.overall`**

| 필드 | 이전 | 이후 |
|---|---|---|
| `totalScore` | LLM 이 면접 전체를 보고 매긴 종합 점수 | 4축 가중합(1.2 계산 규칙) |
| `intentAlignmentScore` | LLM 이 매긴 "물은 것에 답했는가" 점수 | 의도 충족 축 점수 |
| `reliabilityScore` | LLM 이 매긴 일관성 점수(모순·근거 구체성) | (일관성 점수 + 구체성 축 점수) / 2, 정수 반올림. 답변이 1개라 일관성을 판단할 수 없으면 구체성 축 점수 |

**`POST /feedback/multi` 성공 콜백**

- `result.overall` 의 세 점수는 1:1 과 같은 규칙으로 계산한다.
- `result.personas[].score`

| 이전 | 이후 |
|---|---|
| LLM 이 그 면접관 담당 문항을 보고 매긴 점수. 담당 답변이 없으면 0 | 그 면접관이 담당한 답변에만 1.2 공식을 적용한 값. 담당 답변이 없으면 0(계약상 null 불가라 유지) |

**그대로인 필드**: `summary`, `strengths`, `improvements`, `frequentWords`, `answeredCount`, `questionCount`,
문항별 `feedbacks[]` 전체(`modelAnswer`, `strengths`, `improvements`, `comment` 등), 면접관별 `comment` / `strengths` / `improvements`.

### 1.4 실패 콜백 조건 추가

LLM 이 어떤 문항의 축 등급을 빠뜨리거나 0~4 범위를 벗어난 값을 내면, 그 문항은 **피드백 누락과 같은 것으로 보고 실패 콜백**을 보낸다.
형식과 상태 코드는 기존 누락 실패와 같다.

| 엔드포인트 | statusCode | message |
|---|---|---|
| `/feedback/solo` | 500 | 일부 문항의 피드백이 생성되지 않았습니다. |
| `/feedback/multi` | 500 | 일부 채점 결과가 생성되지 않았습니다. |

세션 단위 일관성 등급이 빠지거나 잘못된 경우는 실패로 보지 않는다. 종합 점수에 들어가지 않는 보조 지표라 "판단 불가"로 두고 진행한다.

### 1.5 N:1 요청의 `personas[].role` 값

정확성 축은 **기술 면접관의 문항에만** 적용한다. 서버는 `role` 의 앞뒤 공백을 지우고 대문자로 바꾼 값이 `TECH` 인지로 판단한다.
`TECH` 가 아닌 면접관(HR, CEO, PM 등)의 문항은 LLM 이 정확성 등급을 내더라도 서버가 해당 없음으로 바꾼다.

기존에도 `techPersona.role` 은 `TECH` 로 보내고 있으므로 API 서버가 바꿀 것은 없다.
다만 기술 면접관의 `role` 을 다른 문자열로 보내면 정확성 축이 빠진 점수가 나온다.

### 1.6 API 서버가 알고 있어야 할 영향

- **점수 분포가 달라진다.** 이전 LLM 산출값은 70~80점대에 몰리는 경향이 있었고, 새 계산값은 더 넓게 퍼질 수 있다.
  적용 시점 전후로 저장된 점수를 같은 기준으로 비교하면 안 된다. 통계·추이 화면이 있다면 적용 시점을 기준으로 구분해야 한다.
- **축별 산출 근거는 아직 콜백에 없다.** 분석 서버 로그(`feedback_solo.dispatch.graded`, `feedback_multi.dispatch.graded`)에
  `scoring_version`, `axis_scores`, `weights`, `consistency`, `question_levels` 로만 남는다.

## 2. 다음 단계 계약 변경안 (미적용 — 합의 필요)

목표: 사용자 화면에 아래처럼 종합 점수의 산출 과정을 보여준다.

```
의도 충족  88점 × 35%
깊이       38점 × 25%
구체성     63점 × 25%
정확성    100점 × 15%
──────────────────
최종 71점
```

### 2.1 추가 필드안 — `result.overall.scoreBreakdown` (solo / multi 공통)

```json
{
  "overall": {
    "totalScore": 71,
    "intentAlignmentScore": 88,
    "reliabilityScore": 69,
    "scoreBreakdown": {
      "scoringVersion": "axis-v1",
      "axes": [
        { "axis": "INTENT", "score": 88, "weight": 35 },
        { "axis": "DEPTH", "score": 38, "weight": 25 },
        { "axis": "SPECIFICITY", "score": 63, "weight": 25 },
        { "axis": "ACCURACY", "score": 100, "weight": 15 }
      ],
      "consistencyScore": 75
    }
  }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `scoringVersion` | string | 채점 방식 버전. 방식이 바뀌면 올라간다. 저장해 두면 전후 점수를 구분할 수 있다. |
| `axes[].axis` | string enum | `INTENT` / `DEPTH` / `SPECIFICITY` / `ACCURACY`. 표시 이름은 클라이언트가 정한다. |
| `axes[].score` | integer \| null | 0~100. 세션 전체가 해당 없는 축(주로 `ACCURACY`)은 null |
| `axes[].weight` | integer \| null | 실제 적용된 가중치(%). 해당 없는 축은 null이고, 이때 나머지 가중치 합은 100이 아니다 |
| `consistencyScore` | integer \| null | 0~100. 답변이 1개면 null. 종합 점수에는 들어가지 않는다 |

- 표시된 축 점수와 가중치로 계산한 값은 `totalScore` 와 항상 일치한다(`Σ score×weight / Σ weight` 를 정수 반올림).
- 기존 세 필드는 그대로 두므로 하위 호환된다.

### 2.2 함께 정할 항목

| 항목 | 제안 | 비고 |
|---|---|---|
| 문항별 축 점수 노출 | `feedbacks[].axisScores`(축별 0~100 또는 null) 추가 여부 결정 | 상세 화면에서 문항마다 약점을 보여줄 때 필요. 필요 없으면 생략 |
| `personas[].score` 담당 답변 없음 | 0 대신 null 허용 | 지금은 "0점"과 "평가 대상 없음"을 구분할 수 없다 |
| 면접관별 산출 근거 | `personas[].scoreBreakdown` 추가 여부 | 1:1 과 같은 구조 재사용 |
| 축 판정 이유 | 싣지 않음 | 토큰 절감 결정. 이유는 문항별 `improvements` 가 담당한다 |
